## Context

The gateway keeps request buckets, token buckets and monthly spend in one Redis per region, reached through one go-redis client per instance with no internal retries. Every store call on the request path and in finalizers runs under a 250 ms context deadline; lease refunds have their own 250 ms each. A failed admission, token charge or budget read fails open with a warning and a `fail_open` entry on the cost event, or refuses a fail-closed tenant with 503 `store_unavailable`; a failed reconciliation, spend increment or lease refund is logged or counted as lost. The store-outage run measured the price of that bound being per call: a hung store adds 250 ms per decision for the whole outage.

## Goals / Non-Goals

Goals: after the store fails repeatedly, skip it on this instance for a cool-down so decisions are made at once under the tenant's policy; resume on the first probe the store answers; keep the healthy path unchanged; measure detection, latency and recovery with the existing harness. Non-goals: sharing gate state between instances, making limits exact during an outage, retrying store calls, or changing what fail open and fail closed mean.

## Decisions

- **Reuse `internal/breaker`.** The gate needs exactly what the backend breaker already implements and measures: a sliding window of outcomes with a minimum sample, a failure-rate threshold, a cool-down, a bounded number of half-open probes, tickets whose outcome counts only in the state that admitted them, and a transition hook. A new state machine would repeat that logic with its own bugs. The breaker gains one accessor, `Ticket.Probe`, so the gate can tell a half-open probe from a closed admission without a second, racy state read.
- **Rule: 20 calls, at least 10, more than half failed.** The breaker's defaults. With a full window of successes the gate opens on the 11th failure; a burst of slow calls on a healthy store does not open it, and the arithmetic matches the backend breaker's published detection. A consecutive-failures rule was considered: it reacts a few calls sooner but trips on a partial failure rate by chance and resets on any interleaved success, so its behavior depends on traffic interleaving rather than on a stated rate.
- **What a failure is.** A call the store did not answer: a deadline, a connection or dial error, a pool timeout. A reply — including Redis error replies and nil — is a success: the store answered. A call whose caller canceled its context records nothing, as for backend attempts.
- **Where the gate sits: the store client.** The gate is a go-redis hook on the instance's single client, so every store call is covered — strict admission, lease acquisition and refunds, token charge and reconciliation, budget read and spend increment — without changing their callers. A skipped call returns `storegate.ErrOpen` immediately; callers already treat any store error as unavailability, so fail-open records, fail-closed refusals, lost increments and lost refunds follow unchanged. Commands go-redis issues while setting up a connection run inside the call that dialed and are judged with it, not counted again.
- **Probe: one background PING per cool-down.** After 1 s open, the first store call moves the breaker to half-open and takes its single probe slot for a `PING` bounded by 250 ms, run in its own goroutine; the call that triggered it and every call until the probe ends are skipped. An answer closes the gate with a fresh window; anything else reopens it for another second. Letting a real call through as the probe was considered: with a hung store it makes one request per cool-down per replica wait 250 ms; the PING keeps every request fast once the gate is open.
- **Cool-down 1 s.** While open the gate costs one PING per second per instance, the same rate as the Redis client's own dial probe. After the store recovers, decisions keep being skipped for at most one cool-down plus one inter-arrival per instance: fail-open tenants are admitted without a decision and fail-closed tenants refused for up to about a second longer than the outage. A longer cool-down lengthens that tail for no benefit, since the probe costs no request.
- **No configuration.** The rule, cool-down and probe budget are constants announced in the startup log. The backend breaker's settings (`PUSAQ_BREAKER_*`) tune upstream detection and stay separate.
- **Observability.** Each transition is logged as `breaker_state` with `component` `store`, `from` and `to`, the same message as backend transitions with a field that tells them apart. The event report lists them in its rate-limiting view; the store-outage harness collects them per replica, and the verifier reports when each replica's gate opened and closed and fails when a gate opens before the injection, never opens during a window in which its replica met store failures, or is still open when the run ends.

## Risks / Trade-offs

- **Detection is not free.** About 11 failed calls per instance happen before the gate opens; with a hung store each of them waits its 250 ms, so the slowest requests of an outage keep the old latency.
- **Recovery waits for a probe.** An instance with no store traffic stays open: the first call after the cool-down is skipped and starts the probe. Admissions without a decision and fail-closed refusals continue for up to one cool-down after the store answers again.
- **A store that answers PING but not scripts** would close the gate and open it again every cycle of 11 failures: bounded, visible in the transition records, not prevented.
- **Per instance.** Replicas detect and recover separately; nothing is shared between them, and limits during an outage are as inexact as before (constitution rule 6).
